# AI 记账助手 V1 产品需求文档（PRD）

## 1. 产品概述

### 1.1 产品定位

基于 AI 自然语言理解的消费管理助手，帮助用户从消费数据中发现规律、理解消费行为，并将认知转化为行动。

### 1.2 产品背景

传统记账工具能够记录消费、统计金额和展示消费分类，但用户仍需要自行理解数据、寻找消费变化的原因，并决定是否调整消费习惯。

本产品希望利用 AI 的自然语言理解、数据解释和多轮交互能力，降低用户理解消费数据的门槛。

### 1.3 产品目标

1. 降低用户记录和查看消费数据的操作成本。
2. 帮助用户快速发现值得关注的消费变化。
3. 通过数据证据和多轮交互，帮助用户理解消费行为。
4. 为用户提供可选的消费管理建议。

### 1.4 V1 核心范围

**本期包含：**

* 账单导入及数据校验。
* 消费金额统计与对比。
* AI 消费分析与自然语言问答。
* 消费变化的证据展示。
* 异常情况提示及后续操作引导。

**本期暂不作为核心交付：**

* 自动制定并执行完整的个人财务规划。
* 无充分证据时自动推断消费原因。
* 自动调整用户预算或代替用户做消费决策。

## 2. 目标用户与核心场景

### 2.1 目标场景

用户已经导入账单，希望了解自己的消费情况，但不清楚哪些变化值得关注，以及这些变化意味着什么。

### 2.2 核心用户故事

作为一名希望更好管理消费的用户，我希望系统能够分析我的账单，指出重要的消费变化，并允许我进一步追问，从而更好地理解自己的消费行为。

## 3. 核心用户体验流程

1. 用户进入首页，查看今日消费、预算信息，并使用对话入口。
2. 用户导入账单，系统校验数据完整性。
3. 系统计算消费总额、分类金额及周期变化。
4. AI 展示关键发现、数据依据和可选的深入分析入口。
5. 用户可以查看账单、追问消费变化，或结束分析。
6. 系统根据可用数据继续分析；数据不足时明确说明限制。
7. 用户查看分析结果，自主决定是否采取行动。

核心原则：程序负责准确计算，AI 负责解释和交互；系统帮助用户形成认知，但不强制用户完成分析或采纳建议。

## 4. 功能需求

### FR-01：首页与对话入口

**需求描述：**
首页提供快速记账和 AI 对话入口，并展示必要的消费概览。

**功能规则：**

* 展示今日消费及预算使用情况（有预算数据时）。
* 提供账单导入入口。
* 提供自然语言对话入口。
* 首次使用且没有账单时，优先引导用户导入账单。
* 可以展示明确标注的示例分析，但不得将示例误显示为用户真实数据。

### FR-02：账单导入与数据校验

**需求描述：**
用户导入账单后，系统应检查数据是否可用于后续分析。

**功能规则：**

* 检查导入文件是否能够正常解析。
* 检查必要字段是否存在。
* 识别重复记录及异常数据。
* 尽可能告知用户账单来源、覆盖周期和数据缺口。
* 当用户只导入部分平台账单时，不得默认其覆盖全部消费。

### FR-03：消费统计与变化识别

**需求描述：**
系统通过程序计算消费指标，为 AI 提供可信的数据依据。

**功能规则：**

* 计算指定周期的消费总额。
* 计算不同消费类别的金额。
* 对比两个周期的金额差值。
* 当对比基数大于零时，计算相应增长率。
* 在数据允许的情况下识别新增消费记录和金额明显变化的记录。
* 缺少必要数据时，不生成没有依据的比较结论。

### FR-04：AI 消费分析

**需求描述：**
AI 根据计算结果及账单证据，用自然语言帮助用户理解消费变化。

**功能规则：**

* 优先展示重要发现及其数据依据。
* 对关键变化进行清晰、易理解的解释。
* 仅将有数据支持的内容表述为事实。
* 无法确认具体原因时，明确说明当前证据不足。
* 根据用户需求提供后续探索入口。
* 不得将相关性或金额变化直接当作确定的因果关系。

### FR-05：多轮对话与深入探索

**需求描述：**
用户可以针对分析结果继续提问。

**功能规则：**

* 支持用户查看相关账单。
* 支持用户追问消费变化。
* 数据不足时，可以请求用户补充相关背景。
* 支持用户随时结束分析。
* 不得强制用户持续对话或接受建议。
* 用户结束分析时，可以总结已确认的发现和仍未确定的问题。

### FR-06：消费建议与行动引导

**需求描述：**
在分析结果能够支持的情况下，系统提供可选的下一步行动。

**功能规则：**

* 建议应与已发现的问题相关。
* 建议应具有可执行性。
* 不得把预算调整或消费减少作为所有场景的默认答案。
* 用户可以选择接受、忽略或进一步讨论建议。
* 涉及预算设置等具体操作时，应由用户确认后执行。

## 5. 关键交互示例

### 场景 A：具备两个月账单

用户询问：“为什么我这个月花了这么多钱？”

系统查询到：

* 上月总消费：¥3,200。
* 本月总消费：¥3,980。
* 总消费增加：¥780，约 24.4%。
* 餐饮支出由 ¥850 增至 ¥1,280，增加 ¥430，约 50.6%。

AI 回复应说明总消费和餐饮支出的变化，并提供查看餐饮账单、继续探索原因等入口。

如果无法确认消费增加的具体原因，应明确说明，而不是编造原因。

### 场景 B：只有本月账单

用户只导入了本月支付宝账单，没有上月数据。

AI 应：

1. 展示当前能够确认的消费金额。
2. 明确告知缺少上月数据，暂时无法进行环比分析。
3. 提供导入历史账单或分析本月消费结构的选项。

系统不得虚构上月金额、增长率或消费增长原因。

## 6. 异常处理与边界条件

| 异常情况      | 系统处理规则                       |
| --------- | ---------------------------- |
| 缺少历史账单    | 不进行无依据的周期比较，提供补充数据或分析当前周期的选项 |
| 只导入部分平台账单 | 明确提示数据覆盖范围，不将部分数据直接视为全部消费    |
| 消费类别缺失    | 展示未分类数据，避免遗漏或擅自归类            |
| 数据存在重复记录  | 按确定的去重规则处理，并避免重复统计           |
| 无法确认消费原因  | 展示已确认的事实，明确说明原因尚未确认          |
| AI 分析失败   | 告知用户分析暂时不可用；在条件允许时保留基础统计结果   |
| 用户不愿继续探索  | 允许用户结束分析，不强制追问               |
| 对比基数为零    | 展示金额变化，不直接计算或展示无意义的常规增长率     |

## 7. 验收标准

### AC-01：金额计算准确

测试数据：

* 上月餐饮消费：¥850。
* 本月餐饮消费：¥1,280。

预期结果：

* 金额差值为 ¥430。
* 增长率约为 50.6%。

### AC-02：缺少历史数据时不编造

测试条件：只有本月账单，没有上月账单。

通过条件：

* 不输出虚构的上月消费金额。
* 不输出缺乏依据的环比增长率。
* 明确说明无法进行周期比较。
* 至少提供一种可执行的下一步操作。

### AC-03：AI 解释有依据

测试条件：餐饮支出增加 ¥430，但没有足够信息确认具体原因。

通过条件：

* 能准确展示已计算的金额变化。
* 不将未经证实的原因描述为事实。
* 能明确区分已确认发现和待确认原因。

### AC-04：用户能够自主结束分析

测试条件：用户查看分析后选择结束。

通过条件：

* 系统允许用户结束分析。
* 不强制要求用户回答后续问题。
* 不强制要求用户接受建议。

### AC-05：数据覆盖范围明确

测试条件：用户只导入支付宝账单。

通过条件：

* 系统能够识别当前导入数据的来源范围。
* 不将当前数据直接宣称为用户全部平台的消费总额。

## 8. 待验证事项

以下内容仍属于产品假设，需要通过用户调研或原型测试验证：

1. 用户是否更偏好对话式首页，还是统计概览式首页。
2. 用户是否愿意主动导入账单，以及主要阻碍是什么。
3. 用户是否需要系统主动推送消费分析。
4. 用户更喜欢文字解释、图表，还是文字与图表结合。
5. 用户是否会根据分析结果调整消费行为。

验证结果应影响后续迭代，不应在缺少证据时直接认定这些设计已经满足用户需求。
